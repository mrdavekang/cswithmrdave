# Live FOR-loops setup

This is a separate feature in the existing classroom Supabase project. Its SQL creates only `y10_for_private` objects and `public.y10_for_*` functions; it does not replace or alter existing classroom tables, functions, lessons, policies, or Realtime channels.

1. Keep the existing public `CLASSROOM_CONFIG` URL/publishable key in this lesson. Never put a service-role/secret key, teacher password, or student export in a published lesson folder.
2. In that project's SQL Editor, run the whole `01-live-for-loops.sql` file. It checks for the existing approved-teacher/class mapping and locates the installed `pgcrypto` schema automatically. If `pgcrypto` is absent, enable it under Database → Extensions and rerun. There is no need to enable anonymous Auth or change any Auth setting.
3. Run `02-student-permalink.sql` in the same SQL Editor. It checks the existing pupil functions before replacing them and adds a fixed-Year-10 entry route. It also hides live code and released pages from pending/declined pupils. No teacher grants, tables, class ownership or Auth settings change.
4. Open the lesson's teacher view. Sign in with the existing classroom account that owns class `c429701c-21c3-4e99-b84d-c2faadca7afb`, then start the classroom. A different approved teacher still cannot control this class. Copy the permanent lesson link from Class responses → Permanent student link and admission, and share it in Teams. Students open that same URL each time, enter their name and choose Start lesson. If no class is running they can wait (checked every eight seconds), stop waiting or practise independently. Admit recognisable pending names on the teacher board. Names alone are not verified identities; check the pupil/device when duplicate or unexpected names appear. A fresh session requires new admission; no new invitation is needed.
5. Present or Work makes the selected stage viewable. Use **Work** to permit saving; previously released stages remain available while in Work mode. Present and Paused stop all lesson-work writes at the server. An individual unlock adds permission for a stage but does not override Present/Paused. Help requests remain available to admitted students while paused.

## Privacy and retention

The browser makes a random 256-bit device token. Only its SHA-256 hash is stored in the database; the raw token remains in browser storage and is sent only to the private RPC over HTTPS. Never copy browser storage, RPC payloads, device tokens or private teacher-board screenshots into the public repository. Clearing site data loses the token: that pupil joins again and needs admission again. Shared devices should use a separate browser profile, clear their private join when handing over, or use the lesson's change-pupil action.

Students can retrieve only their own name, work, admission state and feedback. They cannot list the roster, read another pupil's work or issue teacher commands. The permanent entry route discovers only the active, unexpired room belonging to this fixed class's existing approved owner. It is an admission request, not identity verification. Pending/declined pupils receive Get ready/Paused, no released pages and an empty live demonstration; they cannot save or request help until admitted. Both permanent and legacy room-specific joins use the same token and admission checks. All teacher commands recheck both approved-teacher status and the pre-existing class owner. Tables have RLS and no direct browser access; only individually granted RPCs are exposed. There are no new Auth users, no anonymous-Auth setting changes and no public Realtime channel. Teacher authentication uses session storage separate from all student requests. A response already in flight when admission is withdrawn may contain the previously admitted snapshot; revocation takes effect on subsequent requests.

The live session expires after four hours. Expiry/end prevents further work writes but does **not** delete evidence; a pupil may still retrieve their own saved work and feedback. Starting another session creates separate rows. Keep named pupil work for no more than seven days unless the school requires a different period. An authorized database operator should review/export privately, then remove only the selected old `y10_for_private.y10_for_rooms` rows; their pupil rows cascade. This setup does not schedule a purge or automatically delete any data. Database backups may retain removed data according to the school's Supabase backup policy. Local lesson drafts also remain on the device until deliberately cleared.

Each stage stores only the latest answers/code plus at most eight recent execution outcomes. Each run includes the source and input snapshot that actually produced its output, independently of the latest edited draft. No keystroke history is stored. Payload limits: answers 12 KB, source 20,000 characters, each output/error field 8,000 characters, eight bounded runs, 90 KB per run, 760 KB per one-stage save and 4 MB per pupil. Inputs are bounded to 100 strings and 8 KB total. The roster is capped at 100 joins per session, including rejected joins: if unexpected joins exhaust the list, end the session and start a fresh one. Name-only joining is not a public abuse-proof service: use the normal school lesson link, admit only expected pupils and monitor unexpected joins.

## Verification before classroom use

Use two separate student browser profiles and the signed-in teacher view. Confirm: permanent entry waits if no class is running; joins wait pending with no live demo; a rejected/pending pupil cannot save or read released stages; the teacher admits pupils; work appears on the teacher board; Present/Paused and unreleased stages reject writes while preserving local drafts; individual unlock works only in Work mode; feedback is private to its pupil; another account cannot control/read the class board; ending the session blocks further work writes. The same permanent URL must find a newly started room rather than an older saved room. Changing a pupil ID or room ID without its matching token must not reveal any work.

These checks require the SQL to have been run. Local HTML/JavaScript validation alone does not prove deployed database permissions. No Supabase changes are performed merely by opening or delivering this folder.
